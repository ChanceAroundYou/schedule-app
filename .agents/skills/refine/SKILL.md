# Refine：需求收敛

把一句模糊需求收敛成四项可执行结论，然后交给 Plan 阶段。本 Skill 的边界很窄：
**只收敛需求，不设计实现，不写文件，不跑命令，不做审查。**

> 下游是 **Plan 阶段**（调查根因 → 方案 → 计划 → 用户确认），由当前会话直接执行，不再经过多角色工作流。
> 收敛结果就是 Plan 阶段的输入。本 Skill 不调用、不依赖 `devflow`。

## 何时触发

用户表达了一个需要落地的请求，且满足以下任一条件：

- 需求描述模糊、边界不清
- 涉及多文件修改、布局排版变更、算法设计调整等多步骤任务
- 存在多种理解走向，需要用户拍板

典型信号：

- "复盘一下今天的工作"
- "总结一下经验和教训"
- "帮我整理一下 xxx"
- "你看看这个怎么做"
- "我有一个想法但说不清楚"

## 何时跳过

- 纯问答 / 查资料 / 读文件这类**不产生改动**的小事：直接回答，不进本流程。
- 用户明确说"直接做 / 别问了"：跳过收敛，但仍需把 scope/exclusions/deliverables/acceptance
  用一两句话说清再动手，不默认闷头干。

## 铁律

**需求收敛完成前，不做任何执行动作** —— 不搜索、不读文件、不写代码、不跑命令、不碰 git、
不讨论实现方案。四项收敛结论经用户确认后，才交给 Plan 阶段。

这条是本流程存在的唯一理由。违反它，追问就退化成"边做边问"，用户付了确认成本却拿不到确认价值。

## 流程

### Step 0 — 拆解复述

用自己的话重述需求，列出拆解出的子任务：

> 你说的 X，我的理解包括：
> - 任务 A
> - 任务 B
>
> 对吗？

必须等用户明确回复"确认/可以/对"才继续。沉默或模棱两可不算确认。

### Step 1 — 展开（仅当需求太短）

把一句话需求展开到可讨论的详细程度，补充隐含范围，但不展开成完整方案：

> 你提到 X，可能涉及的范围：
> - ...
>
> 哪些是你要的？哪些不是？

### Step 2 — 逐轮追问（每轮 1–2 个）

按四项收敛目标依次追问，一次只问 1–2 个，等答复再继续：

| 收敛项 | 要问清的东西 |
|--------|--------------|
| **scope** | 具体做哪几件事？边界到哪？ |
| **exclusions** | 明确不做什么？（含不能动的文件/分支/环境） |
| **deliverables** | 交付物是什么形态、放哪里、给谁用？ |
| **acceptance** | 做到什么程度算完成？怎么验证？ |

不要一次抛全部问题。

### Step 3 — 输出四项收敛结论

```markdown
## 需求收敛结果

### scope（做什么）
- [ ] ...
- [ ] ...

### exclusions（不做什么）
- ...

### deliverables（交付什么）
- 形态 / 路径 / 使用者

### acceptance（怎样算完成）
- 可判定的标准 1
- 可判定的标准 2
```

用户确认后进入 Step 4。

### Step 4 — 移交 Plan 阶段（本流程终点）

用户确认四项结论后，明确告知：

> 需求已收敛，接下来进入 Plan 阶段：先调查根因、给方案与取舍，再出计划等你确认。

然后进入 Plan 阶段。**本 Skill 到此结束**：

- 不做"选哪条工作流"的分流：需求涉及代码/配置/项目文件改动 → 一律转 Plan 阶段；
  纯讨论类需求 → 交付结论后直接结束。
- 不写实现、不写计划文件、不跑命令、不碰 git、不提交、不发版。
- 不指定子 agent、不派发子 agent、不做独立审查。

## 原则

1. **只问选项式或 yes/no 问题**，不把判断成本推回给用户。
2. **逐轮追问**，每次停下来等回答，不连珠炮。
3. **四项收敛是唯一交付物**，不夹带方案设计。
4. **中途新增需求另起一条**，不塞进当前需求。
5. **自己是收敛器，不是总管**：出完四项结论就交棒，执行与审查都不在本 Skill。

## 反面教材

- 收到"整理一下 xxx"就直接搜索、读文件、交总结 —— 用户没确认过范围。
- Step 0 发完复述没等确认就动手。
- 一次抛出十几个问题让用户填表。
- 收敛阶段就开始讲"我打算改哪几个文件、怎么改" —— 那是 Plan 阶段的事。
- 收敛完自己闷头写代码/提交/发版。
- 把"要不要走工作流"当成闸门去自动判定并转交给某个执行流程 —— 收敛完只交 Plan 阶段。
