# Prompt Refine + 方案闸门

把一句模糊需求转化为边界清晰、可直接执行的方案，并作为工作流的**入口闸门**：
判断这个任务该不该进入"执行 → 提交 → 审查 → 同步 → 发版"的完整工作流。

**核心是本技能的"打磨对话"**：Step 0~3 用「复述 → 展开 → 逐轮追问（每次 1-2 个）→
输出结构化需求」，把"我想做 xxx 但说不清楚"变成可落地的 prompt。这套追问流程本身
也可沉淀为可复用工作流（例如固化成 Skill）。闸门（Step 4）只是打磨完之后的分叉：
进 `devflow` 还是只给方案。

> 本 skill 是**入口，不是总管**。**出方案归我，跑执行归 `devflow`**。
> 发版 / 同步 / 报障分别交给 `schedule-deploy` / `schedule-sync` / `schedule-bug`
> （由 devflow 在流程中调用，不在本 skill 出现）。

## 总览

1. **先出方案（默认）** —— 见下方 Step 0~3。用户没确认前不动手。
2. **方案确认后做闸门判断**：
   - **会改代码 / 文件 / 配置 / 线上** → 自动交接 `devflow` 跑完整工作流
     （执行 → 提交 → 审查 → 同步 → 问发版）。
   - **纯问答 / 查资料 / 闲聊 / 只读分析 / 纯方案讨论** → 只给方案，**停在这里**，不进工作流。

## 何时触发

用户表达了一个需要执行的请求，且满足以下任一条件：

- 需求描述模糊、边界不清
- 涉及多文件修改、布局排版变更、算法设计调整等多步骤任务
- 存在多种理解走向或方案选择，需要用户拍板

典型信号：

- "复盘一下今天的工作"
- "总结一下经验和教训"
- "帮我整理一下 xxx"
- "你看看这个怎么做"
- "我有一个想法但说不清楚"
- 任何需要做设计决策（超过单函数 / 单文件变更）的任务

## 何时跳过（范围收窄）

默认**走本流程、先出方案**。只在以下情况跳过，直接做：

- 纯问答 / 查资料 / 读文件这类**不产生改动**的小事（本流程闸门也会判为"不进工作流"，只给答案）；
- 用户明确说"直接做 / 别出方案了"。

**凡是会改动代码、文件、配置、线上内容的任务，一律先出方案再动手** ——
哪怕用户描述得很清楚，也用一两句话把"我打算怎么改、改完怎么验证"摆出来确认，
不默认闷头干。这是和「纯小白 vibe coder」协作时避免返工的关键。

## 铁律

**scope 确认前，不做任何执行动作** —— 不搜索、不读文件、不写代码、不执行 git 命令、
不讨论实现方案、更不提交 / 发版。所有理解确认后再动。

这条是本工作流存在的唯一理由。违反它，追问就退化成了"边做边问"，
用户既付出了确认成本，又拿不到确认的价值。

## 流程

### Step 0 — 拆解复述（绝对第一步）

用自己的话重新表述用户的需求，标注拆解出的子任务：

> 你说的 X，我的理解包括了：
> - 任务 A
> - 任务 B
>
> 对吗？

**必须等用户明确回复"确认"或"可以"，才能进入下一步。**
沉默或模棱两可的回应不算确认。

### Step 1 — 展开（仅当需求太短）

如果原需求只是一句话，展开到合理的详细程度，补充隐含的前提和可选范围：

> 你提到 X，我展开一下可能涉及的范围：
> - ...
> - ...
>
> 哪些是你想要的？哪些不是？

不要一次性展开到"完整方案"的程度 —— 只是让短需求变成长度合适的可讨论基线。

### Step 2 — 追问收窄（每轮 1-2 个问题）

按优先级依次追问，**一次只问 1-2 个**，等用户回答后再继续：

| 维度 | 问题示例 |
|------|---------|
| **Scope** | 你说的 X，是只做 A 还是连 B、C 一起？ |
| **产出物** | 输出的东西给谁看的？AI 还是人？放在哪里？ |
| **粒度** | 你要具体踩坑记录还是抽象原则？ |
| **排除** | 有没有明确不做的？ |
| **验收** | 做到什么程度算完？ |

不要一次抛全部问题。每次追问后停下来等回答。

### Step 3 — 输出结构化需求

用以下模板输出：

```markdown
## 结构化需求

### Scope（要做）
- [ ] 任务 A
- [ ] 任务 B

### 排除（不做）
- 任务 C

### 交付标准
- 标准 1
- 标准 2

### 输出位置（给谁看、放哪）
- `.workbuddy/memory/YYYY-MM-DD.md` —— 给 AI 看的每日记忆（沉淀踩坑 / 决策）
- `.workbuddy/memory/MEMORY.md` —— 跨会话长期记忆
- `rules/xxx.md` —— 约束性规则（如编码规范、性能红线）
- `docs/xxx.md` —— 给人看的设计 / 说明文档
- `~/.workbuddy/skills/<name>/SKILL.md` —— 做成可复用的 Skill
```

让用户确认后再进入闸门判断。

### Step 4 — 确认 + 闸门判断（本流程终点）

用户确认方案后，做一道**闸门判断**，决定要不要进入工作流：

- **会改代码 / 文件 / 配置 / 线上内容**（开发任务）→
  明确告诉用户："方案确认，接下来按工作流自动跑（执行 → 提交 → 审查 → 同步 → 问发版）"，
  **自动交接 `devflow`** 接管后续执行。本 skill 到此结束，不再自己写代码 / 提交 / 发版。
- **纯问答 / 查资料 / 闲聊 / 只读分析 / 纯方案讨论**（不改任何东西）→
  只把方案 / 答案交付给用户，**停在这里**，不触发任何执行、不碰 git、不动生产。

> 闸门判据只有一条线：**这个任务会不会改动代码 / 文件 / 配置 / 线上？**
> 会 → 进工作流；不会 → 只出方案。不靠"每次问用户要不要走工作流"，按内容自动判断。

## 原则

1. **不问"你觉得怎么样"** —— 给选项式或 yes/no 问题，开放式提问会把判断成本推回给用户
2. **逐轮追问** —— 每次追问后停下来等回答，不要连珠炮
3. **scope 确认前不写代码、不读文件、不搜索、不讨论方案** —— 一条线画清楚
4. **执行过程中不追加** —— 用户中途说"再做个这个"，记录为新需求，不塞进当前工作
5. **自己是入口，不是总管** —— 出完方案、闸门判完，执行一律交给 `devflow`，绝不自己跑执行

## 反面教材

以下都是违反本工作流的行为：

- 收到"整理一下 xxx"就直接开搜索、读完文件给出一份总结 —— 用户没确认过范围，
  交付的东西大概率不是他想要的
- Step 0 发出复述后，没等到明确确认就开始动手
- Step 2 一次抛出五个维度的全部问题，让用户填表
- 执行到一半发现用户还想要别的，直接顺手做了（scope 膨胀），
  结果交付边界模糊，用户无法判断哪些是原本计划的
- 出完方案后**自己闷头写代码、提交、甚至发了线上** —— 执行是 `devflow` 的事，
  refine 越权就等于跳过了闸门，纯问答也可能被误推进工作流
- 改完自作主张发了线上，没先问用户 —— 发版与否由 `devflow` 每轮问、且要用户亲口说"发"
