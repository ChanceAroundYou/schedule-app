# 项目执行流程（devflow）

> 本 skill 是日程项目的**执行/提交/同步/发版细节参考**，不是工作流入口，也不是 `refine` 的下游。
> 需求收敛归 `refine`；方案、计划、实施与自测由当前会话直接完成（不使用子 agent、不启用三角色流程）。
> 本 skill 只负责"用户确认方案之后"的项目特有收尾细节。
>
> 与用户批准的计划冲突时，**以批准计划为准**，本 skill 让路。
>
> 发版兼容壳 `schedule-deploy`、同步执行器 `schedule-sync`、报障 `schedule-bug`
> 都是本流程调用的底层执行器。

## 触发

- **用户确认方案后收尾**：方案已获用户确认、改动已按计划实施并自测通过，
  按计划把本流程负责的提交/同步/发版步骤交给这里执行；
- **用户直接触发单步动作**（大白话即可）：

| 用户说 | 我做什么 |
|--------|----------|
| "存一下" / "提交" | 只 commit（本地保存，不推不拉） |
| "拉一下" / "下载最新" | 只从 GitHub 拉最新到本地 |
| "推一下" / "上传改动" | commit + 只把本地推到 GitHub |
| "同步一下" | commit + pull + push |
| "发线上" / "发布" | 走发版（**网页端和安卓端默认自动发 + 实测**，顺序先 Web 后 APK，各有对应 e2e：网页 live-check.mjs / 安卓 android-live-check.mjs） |
| "别发" / "先别动线上" | 跳过发布 |
| "看状态" / "现在到哪了" | 汇报进度 |
| "有冲突吗" | 检查本地和云端会不会打架 |

> 单步语义以本表为**唯一来源**；`schedule-sync` 只作底层 push/pull 执行器，不再重复定义这些快捷键。
>
> "审查一下代码"不在本表：代码检查由当前会话按项目测试口径自行完成，本 skill 不提供替代审查。

## 模块索引（执行细节，按需读，不要一次全读）

本 skill 的执行细节拆到 `modules/`，用到哪块读哪块：

| 模块 | 何时读 |

| `modules/workspace-safety.md` | **每次动 git / 发布之前**——并行开发保护硬规则（分支策略、保全、禁止清单，必读） |
| `modules/web-flow.md` | 发版第 1 步：先发网页端（每次版本发布都走） |

## 标准流程（用户确认方案后的项目收尾）

**前置条件**：方案已获用户确认、改动已按计划实施并自测通过。不满足则不做本流程任何一步。

**0. 前置自检 + 抢锁（进任何动作前）**
   - 先读 `modules/preflight.md`：检查 node 版本、gh 登录、Playwright 的 Chrome、以及（若走安卓）adb 连通。缺什么先提示你装/连，别跑到一半挂。
   - 再读 `modules/lock.md`：在仓库 `.git/devflow.lock` 写会话 ID+时间戳抢锁；若锁属其他近期会话，停下报告「另一会话正在跑工作流」，不抢。结束/出错删除锁。

1. **核对改动与计划一致**：确认工作区里的改动就是批准计划列明的那些，没有夹带。
   - 有夹带或超范围 → 停下报告，不提交、不发版。
   - **动 `app/src/views/`、`app/src/styles/` 前先查 `docs/` 定案**（`grep -n 关键词 docs/*.md`，
     关键词如：周视图、锁单屏、拖拽、键盘、时间轴）。设计定案的唯一真相源是 `docs/`，
     不是 AI 记忆——2026-10-24 教训：定案只在记忆里 → 并行会话按旧记忆改回去 →
     用户看到"回退"（6504386 事件）。查到定案 → 遵守；要改定案 → 先问用户。

2. **git commit**：动 git 前**先读 `modules/workspace-safety.md`**，按它的五条保全检查
   （status / stash list / ls-files -u / log / branch）+ 禁止清单执行，绝不误覆盖别人的改动。
   - **提交前轻量校验（拦掉编不过的提交）**：改了前端 TS → `cd app && npx tsc --noEmit`；
     改了 server → `node --test server/tests`；都过再提交。（这步是门前关，不是代码审查。）
   - 只在计划已授权提交时提交；只用 `git add <具体文件>`（不用 `-A`）。

3. **push + pull**：推送前同样按 `modules/workspace-safety.md` 的「推送前安全网」
   体检（先 `pull --rebase`、确认要推的就是本任务那几个提交）。只在计划已授权推送/同步时执行；
   **只动 `dev`，不碰 main / ubuntu 工作区 / 其他分支**；
   **严重冲突无法自动合并时停下问用户**（给选项：保留哪边 / 让我挑重要的），绝不擅自覆盖。
   （分支策略细则见 `modules/workspace-safety.md`，本步骤不重复定义。）

4. **发版 = Web + Android 双渠道，严格先 Web 后 APK（限计划已列明授权）**：
   - **任何项目版本的默认 scope 涵盖两个渠道**，需求规划与计划都应把两渠道写进默认 scope；
     用户无需在需求里另外点名"手机端 / APK"，**也不得反问"要不要发 APK"**。
     但**默认 scope 不等于已获授权**：
     **仅当批准计划正文逐条列明 Web 与 APK 的具体发布、验证步骤**（如具体发布脚本、
     生产 URL 实测、装包与真机校验）**以及所需的外部操作时，计划确认才只授权这些列明动作**。
     **不得推定任何未列明的发布动作、发布渠道或设备操作**（连接设备 / 装包 / 真机操作）**已获授权**；
     计划未列明 → 停下确认，不自行补发、不"顺手"扩展。
     同一任务两侧都获列明授权时，**顺序执行，不并发**：
     网页端跑绿并验收通过后，才开始安卓端；不得同时开两条发布链。
   - **第 1 步 网页端**：读 `modules/web-flow.md`，跑 `./deploy/web-loop.sh`（自动发 +
     `live-check.mjs` 打生产 URL 实测，失败自动返工 ≤3 轮，还不过停下汇报）。
     （注意：`web-loop.sh` 自己就是放行闸，**没有 `--approve` 参数**——那个参数只有
     `publish-server.sh` / `publish-web.sh` / `publish-apk.sh` 有，别给 web-loop 传。）
   - **第 2 步 安卓端**（网页端验收通过后）：读 `modules/android-flow.md`，跑
     `./deploy/mobile-loop.sh`（自动版本号自检 → 打包 → 发布 → 装机 → 版本校验 → 真机冒烟），
     再由 **`app/tests/android-live-check.mjs`**（镜像网页端 `live-check.mjs` 的
     core/now-line/repeat 断言，通过 CDP 打真机 WebView）跑端到端实测：
     `node app/tests/android-live-check.mjs --device <IP:端口>`。连设备/装包/真机回归按需读 `modules/mobile/`。
   - **跳过某渠道的仅有的两种情形**：① 用户明确暂停或排除某个渠道；② 项目发布前置检查
     （可追溯性、版本号同源、gh 登录、adb 连通等）**硬性阻断**该渠道。任一情形都必须**明确报告**
     跳了哪一端、为什么跳，不得静默只发一端。
   - **非项目版本发布**（纯内部技能 / 记忆 / 文档维护，不产生线上版本）→ 发布步骤不适用，
     在汇报里写明"发布：不适用"，不占双渠道默认。
   - **授权边界**：计划确认只覆盖计划内列明的动作，**不得**扩展成任意外部操作授权；
     计划没列明的提交/推送/发布一律不做。
   - **破坏性 / 不确定改动**（改了同步协议、DB schema、鉴权）→ 无论哪端都先问你再发；
     项目另有更具体的安全约束时按项目约束处理。
   - **发版后统一"验证 + 回滚"关卡**：web 看 `live-check.mjs` 断言全绿、安卓看
     `android-live-check.mjs`（兜底用 `mobile-loop.sh` 第七段真机冒烟）；任一失败立刻
     `publish-web.sh --rollback --approve` 或重装上一版 APK，并马上报告你。

5. **汇报 + 落盘纪要**：用一两句大白话在聊天里告诉用户：改了什么、已提交、是否已同步云端、是否已发布、线上实测结论、自测结论。同时读 `modules/report.md`，按模板在 `runs/` 目录存一份结构化发布纪要（以后能翻）。聊天是即时通知，纪要是存档，两者互补。

## 原则

1. **只管收尾，不管方案与实施**：方案、计划、实施与自测由当前会话直接完成；
   本流程只在用户确认方案后执行提交/同步/发版这些项目特有步骤。
2. **前置条件硬拦**：没有用户确认的方案、自测未通过，本流程任何一步都不启动。
3. **先问再动生产（只限破坏性）**：破坏性 / 不确定改动（同步协议、DB schema、鉴权）先问用户；
   严重冲突、严重隐患无论哪端都先问，绝不擅自覆盖或擅自动生产。
4. **复用执行器**：同步交给 `schedule-sync`（只做 push/pull），发版交给 `schedule-deploy`，
   本 skill 只做编排，不重复造轮子。
5. **冲突让路**：与用户批准的计划冲突时，以计划为准。

## 反面教材

- 方案未经用户确认就自己写代码 / 提交 / 发版——越过方案确认门。
- 没跑项目既有的测试与线上实测就把改动发出去——证据不足就上线。
- 计划只批准了改文件，却顺手提交、推送、发版——超出计划授权。
- 严重冲突时擅自覆盖云端——无论哪一步，冲突都先停下来问用户。
- 两个 AI 会话同时跑本流程改同一份副本——必须靠 `modules/lock.md` 的锁互斥，不能靠"看见了就停"的人肉规则。
