## 四、同步协议

### 4.1 设计取舍

调研结论：**没有任何现成方案自带离线同步**。

- Zero 官方文档：「Zero 不支持离线写入」
- Replicache 已归档（最后提交 2022-05-07）
- ElectricSQL 重写为只读
- PocketBase 作者：「有实时订阅，但没有离线/在线同步——这留给用户自行处理」

所以同步层**必须自写**，这反而使「不引入 PocketBase」成为更简单的选择
（省去 JSVM 里写并发逻辑）。

**采用**：服务端权威 + 客户端持久化发件箱 + **按字段 LWW** + 确定性 id。

> **为什么按字段而不是整实体**：op 里本来就只带改动的字段（客户端知道自己改了什么），
> 服务端逐字段比较和逐实体比较的代码量几乎一样。整实体 LWW 会让
> 「手机改标题 + 桌面改日期」变成一方被丢弃。

### 4.2 操作日志

```ts
interface Op {
  opId: string;        // 客户端 UUIDv4 —— 幂等键
  deviceId: string;
  calId: string;       // 归属日程集（服务器靠它查权限）
  ts: number;          // 客户端时钟（Date.now()）
  entity: 'task' | 'habit' | 'project';
  entityId: string;
  fields: Record<string, unknown>;  // 只带改动字段
  deleted?: boolean;
}
```

### 4.3 端点

```http
POST /api/sync
  Authorization: Bearer <jwt>
  { "cursor": 12345, "ops": [ ...本地未发送... ] }
→ 200
  { "cursor": 12346,
    "applied": ["opId…"],          // 被接受的（含幂等跳过的）
    "rejected": [{"opId":"…","reason":"..."}],
    "ops": [ ...服务端自 cursor 以来的改动... ] }
```

单次往返，请求 + 响应同体。**没有 WebSocket / SSE**：

- SSE 没有游标、没有重放、没有顺序保证，PocketBase 的实测教训
- 家庭场景 2–3 台设备，进来就拉一次足够
- 前台每 60s 轮询一次「有没有新 cursor」，代价可忽略

> **落地时的两处出入**（2026-10-06）：响应里那个 `ops` 字段实际叫 **`changes`**，
> 且每条带 `calId`；`cursor: 0` 有特殊含义 —— **表示「给我一份全量快照」**，
> 响应换成 `snapshot`，而不是从 0 开始回吐全部变更。
> 加多账户之后每条 op 还必须带 `calId`（服务器靠它查权限），
> 归属是**主键的一部分**，不是普通同步字段。详见 [接口.md](接口.md)。

### 4.4 服务端表

> **以下是 2026-10-06 重构前的计划快照，部分结构已废弃。** 当前实现见 `server/lib/db.js`。

```sql
-- 用户（账本的 auth.json 单密码 → 多账户）
CREATE TABLE users (
  id TEXT PRIMARY KEY,          -- UUIDv4
  name TEXT NOT NULL,
  salt TEXT NOT NULL,
  hash TEXT NOT NULL,           -- sha256(salt + password)
  created_at INTEGER NOT NULL
);

-- 字段级 LWW 状态 —— 这是同步的核心，不是 实体表
CREATE TABLE field_state (
  user_id   TEXT NOT NULL,
  entity    TEXT NOT NULL,
  entity_id TEXT NOT NULL,
  field     TEXT NOT NULL,
  value     TEXT,                       -- JSON 编码
  ts        INTEGER NOT NULL,
  device_id TEXT NOT NULL,
  PRIMARY KEY (user_id, entity, entity_id, field)
);

-- 幂等：已处理过的 op，用于重放保护。定期按 ts 清理
CREATE TABLE applied_ops (
  user_id TEXT NOT NULL,
  op_id   TEXT NOT NULL,
  ts      INTEGER NOT NULL,
  PRIMARY KEY (user_id, op_id)
);

-- 游标：单调递增，客户端按它拉增量
CREATE SEQUENCE-like: cursor_meta(user_id TEXT PRIMARY KEY, seq INTEGER NOT NULL);

CREATE TABLE changes (          -- 自增游标驱动的变更流水
  user_id TEXT NOT NULL,
  seq     INTEGER NOT NULL,     -- 单调递增
  entity TEXT NOT NULL, entity_id TEXT NOT NULL, field TEXT NOT NULL,
  value TEXT, ts INTEGER NOT NULL, device_id TEXT NOT NULL,
  PRIMARY KEY (user_id, seq)
);
```

**写入是单事务**：`BEGIN IMMEDIATE` → 查 `applied_ops` → 逐字段比较 LWW → 写
`field_state` + `changes` → `COMMIT`。refer 账本 `putDoc()` 的写法。

**LWW 比较**：

```sql
-- 接受条件：更新的时间戳，或同时间戳下更大的 device_id（确定性平局破解）
INSERT INTO field_state … ON CONFLICT(…) DO UPDATE SET …
  WHERE excluded.ts > field_state.ts
     OR (excluded.ts = field_state.ts AND excluded.device_id > field_state.device_id)
```

> **不做 HLC（混合逻辑时钟）。** 家庭场景时钟偏移最多几秒，LWW 在秒级误差下
> 的实际影响是「偶尔某次编辑被覆盖」，可接受。代价是跨设备大批量离线编辑后
> 可能出现非线性顺序 —— 如果实测出问题，再升级到 HLC，届时只需要换
> `ts` 的生成与比较函数，表结构不变。

### 4.5 客户端发件箱

用 **Dexie 4**（IndexedDB 封装，Web + Capacitor 都可用）：

```ts
interface Outbox { opId, deviceId, ts, entity, entityId, fields, deleted }
```

每次编辑：**先写本地 IndexedDB（乐观更新 UI）→ 入队 outbox → 尝试 flush**。
断网时队列留存，下次进前台自动重试。

> **不用 OPFS**：Capacitor 里 OPFS 被拦（配置缺 `headers` 字段，issue #7813）。
> 也不用 `@capacitor-community/sqlite`：其 Web 端依赖 `jeep-sqlite`，
> 最后更新停在 2024-08-16。

**冲突 UI**：LWW 静默合并能覆盖 99% 的情况，不弹窗。只在任务详情里加一条
只读提示，条件是有一次同步里**我推上去的字段，同时也收到了别人的改动**——
那正好是「两边都改过、LWW 已经判完了」的可观测形态（离线改动在回到网上那一轮
自然落进来）。快照不算：那是「我刚进这个集，把历史整份拉下来」，
里面的改动跟「同时」不是一回事，拿它判必然误报成一片。

判定是纯函数（`domain/merge.ts` 的 `findConflicts`），只告诉调用方
「这个字段两边都动过、谁赢」；**显示的是输的那一方的值** —— 赢的那版就在
上面几个输入框里，再说一遍等于没说。提示可逐字段关掉，关掉要落盘，
否则刷新又冒出来，用户会以为没生效。
