## 双会话交替提交，设计定案被覆盖（2026-10-24）

**现象**：用户报「移动端又回退了——周视图变回会上下滚动、一屏放不完，拖拽卡顿、
精度不对」，怀疑代码分叉出了多个并行版本。

**实查**：全仓 1 个 worktree、分支一条直线（main → dev 逐次提交）、`views/` 每个
组件仅一份文件——没有任何分叉。真相：**同一份工作副本上两个 AI 会话交替提交**，
另一会话 2026-10-23 23:26 合入 `6504386`「手机端周视图放开纵向滚动」，
覆盖了 10-22 定案的「周视图锁单屏」。用户体感的「退到旧版本」= 后合入的改动流
覆盖了先定案的行为。

**根因**：设计定案只活在 AI 的会话记忆里，另一个会话看不到 → 想改就改了，
还写着「用户裁决」（其实是误判/转述失真）。

**对策**：
1. **定案必须落 `docs/`**——工程文档是两个会话唯一的共享真相源。
   本次已补：`界面约定-布局.md`「周视图 / 日视图锁单屏」节。
2. devflow 的 `.git/devflow.lock` 只防「同时改」，防不了「先后改坏」——
   合入涉及 docs 里已有定案的改动前，先查文档再动手。
3. 撤销用 `git revert` 保留历史，不 `reset`——误判了能回头；
   revert message 里写清「谁、何时、为什么撤」。
4. 行为级护栏进 smoke：本次补的两条锁单屏断言就是「谁改回滚动版谁红」。

**用户原话**：「怀疑现在的修改已经严重分叉了，有两条以上并行的线，老是改着改着
就退到以前的某一个错误版本里」——排查这类「回退体感」时，先查 worktree / 分支 /
多版本组件三件套，再查提交线上的交替合入。

## 应用内自更新：装完又弹「已安装相同版本」（2026-10-26）

**现象**：真机 2.4.3 → 2.4.4 装成功、能进 App，但紧接着系统又弹一次
「已安装相同版本 / 已安装更高版本」，让用户白点一遍。

**特征**：不是每次都弹。只有「装完那一刻进程被安装器杀掉重启」或「冷启动」的
路径上才出现——热启动点检查更新反而正常。这类「偶发」优先怀疑**时序**，
不要去查包本身。

**四个原因叠在一起**（`app/android/.../AppUpdate.java`，commit `3e31db0` 一起修）：

| 表现 | 查这里 |
|---|---|
| 装完又走一遍安装 | `onResume` 里 `recoverPending` 与 `confirmInstalled` **先后顺序**——必须先确认已装 |
| 明明装上了却当没装 | `confirmInstalled` 只看内存里的 `sPendingVersionCode`，冷启动是 0 → 必须从 SharedPreferences 捞回 `pendingVc` |
| 照着旧包又唤起安装器 | `verifyAndInstall` 没检查「其实已经装上了」→ 抢到锁后先比 `selfVersionCode >= pendingVersionCode` |
| 同一包唤起两次安装器 | `recoverPending` 被 `checkOnLaunch` 与 `onResume` 并发调用 → 加 `sRecovering` 挡重入 |

**验证口径**：装成功后看 `logcat -s AppUpdate:V`，理想序列是「接手烂尾（仅一条）→
已经装上 vc=N，不再重装 → 确认已装上，清掉 pending → 已是最新」。三条缺一条就是没修好。

⚠️ **排障陷阱**：修完之后仍可能看到「已安装相同版本 **旧版本号**」的页面——
先 `am force-stop com.oplus.appdetail` 再冷启动。那多半是 OPPO 安装器上一轮的页面
**残留在任务栈**，不是新唤起的，别据此判定没修好。

## 检查更新「时好时坏」：链路里没有一处说结局（2026-11-07）

**现象**：点「检查更新」，按钮转一下就恢复，有时正常、有时毫无反应，反复修不好。

**根因不是某段逻辑写错，而是整条链路**没人把结局说出来**：
网页调原生 → 原生**一接住调用就回 ok**（`call.resolve({ok:true})`），
后面查到没查到、网络通不通、清单对不对，网页一概不知道。于是「坏」的时候
和「没查」的时候长得一模一样，用户只能说「时好时坏」。

**定案**（`AppUpdate.java` / `WidgetBridge.java` / `data/widget.ts` / `SettingsView.tsx`）：
- `AppUpdate` 增加结局常量 `R_LATEST / R_FOUND / R_MANIFEST_BAD / R_NETWORK /
  R_INSTALLING / R_BAD_APK`，`checkAndPrompt` 的**每条 return 路径**都必须
  回执一次；用 `boolean[] once` 挡重复（匿名内部类只能捕获 final 局部变量）。
- `WidgetBridge.checkUpdate` 等检查真的结束才 resolve，把 status/message/versionName
  带回网页；网页按状态显示「已是最新 / 发现 vX / 清单异常 / 网络不通 / 正在安装」，
  删掉原来那个 800ms 假延迟。
- ⚠️ **漏一条 return 路径 = 网页的「检查中」永远不结束**，比不给回执更糟。
  以后往 `checkAndPrompt` 里加分支，先想「这条回执在哪」。

**顺带补的两道闸**：
- `installApk` 前用 `getPackageArchiveInfo` 核对**包名 + versionCode**。
  SHA-256 只证明「下载到的字节和清单一致」，证明不了「这就是该装的版本」；
  对不上就删包 + 清 24h 冷却 + 说人话，而不是拉一个只会回「应用未安装」的安装器。
  `installApk` 因此改成返回 boolean —— 安装器没拉起来时别谎报「正在打开安装程序」。
- `publish-apk.sh` 发版前校验包名、签名（`apksigner verify --print-certs`）、
  线上 versionCode 严格递增。把「装上才发现不对」提前到发布那一刻。

## 计数器连点「数字乱跳」：两个独立原因（2026-11-07 收口）

用户描述是「快速连点加/减，数字要么闪要么跳回原值」。查下来是两处**不同**的病：

| 症状 | 病因 | 落在哪 |
|---|---|---|
| 闪一下又跳回原值 | 服务端旧快照盖掉本地乐观值 | 网页 `useCounters.merge` 三层保护（inflight / 2s 冷却 / 序号）；桌面 `CounterStore.applyServer` |
| 点一下涨两下 | 队列 at-least-once + 重发无凭据 | 协议层：`counter_ops` 表 + `opId` |

**协议层修法**：客户端每次点击生成 `opId` 跟着请求走；服务端按 `(user_id, op_id)`
认人，**查重 + 改值 + 记账在同一个事务里**完成。
- 查重必须**在事务内**：挪到外面，同一个 opId 的两条并发请求会双双看到「没见过」，
  去重就只在串行重发时有效。
- 合并队列条目时**必须保留原 op** —— 合并的是同一次未确认的点击，换新 op
  等于告诉服务端「这是新的一下」，去重白做。
- 凭据只留 7 天（`pruneOps`），每次写入顺手清。
- 网页端不带 opId 也能用（它没有重发队列），但**并发 +1 的原子性不能动**：
  `value = value + ?` 那条语句是另一回事，深测里有一条专门守它。

## 窄屏加控件：先算这一排的账，再决定放哪（2026-11-07）

「按创建者筛选」第一版塞进副header 的日期导航那一排，窄屏就出了事：
四个日期钮 174 + 视图切换 178 = 352，**可用只有 364，只剩 12px**，而筛选项要 107px。
视图切换被挤到第二行 → 副header 53px → 93px → 手机周视图少 40px →
「锁单屏」装不下 → 深测报 3px 纵向溢出。

**结论**：手机上每个新控件都要先算「这一排还剩多少像素」。
更省事的判据是**量高度**：副header 一行 53px、两行 93px，差 40px 一眼看得出。
⚠️ 别用「数 children 的 top 有几组」判行数 —— 34px 与 36px 的控件在
`align-items:center` 下顶边天然差 1px，会数出假的两行。
