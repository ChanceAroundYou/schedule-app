# 工作区保护（多人 · 多端 · 多会话并行）

> 适用范围：日程清单仓库的所有 git 操作与发布动作。
> 定位：**这是硬规则，不是建议。** 与 AGENTS.md「五、工作约束」同级。
> 相关：[DEPLOY.md](../DEPLOY.md)「二、双端开发与生产锁定」、refine skill `modules/workspace-safety.md`。

## 为什么要有这一份

同一个仓库同时被这些角色改着：

| 角色 | 位置 | 分支 | 改什么 |
|---|---|---|---|
| Windows 本机会话 | `C:\Users\小哭包\coding\schedule-wt` | `dev`（remote `github`） | 网页端、日历、手机端打包 |
| **另一个并行 AI 会话** | 同上（同一份工作副本！） | `dev` | 可能是打卡、重复任务等**别的任务** |
| ubuntu 工程目录 | `/mnt/fnos/family/星星包/coding/日程管理`（NAS 本机的同一个目录：`/vol2/@team/family/星星包/coding/日程管理`） | `main`（remote `origin`） | **只读**，禁止改动（用户明确要求） |
| 手机 / 网页用户 | 通过界面 | — | 改的是**数据**，不是代码 |

⚠️ 最危险的组合：**两个会话共用同一份工作副本**。你看到的「未提交改动」很可能
是另一个会话正在做的工作 —— 覆盖它等于凭空删掉别人刚做的事。

## 一、铁律（违反即视为事故）

### 1.1 禁止使用这些命令

```
git checkout -- <file>      git restore <file>      git checkout .
git reset --hard            git reset --hard HEAD~n
git clean -fd               git clean -fdx
git branch -D               git push --force / --force-with-lease
git stash drop              git stash clear
git commit --amend（别人已推的提交）
```

理由：这些命令会**静默丢弃**正在进行的修改，且事后无痕迹可追。
（例外：用户明确点名要求，且已确认备份点存在 —— 仍要先留备份。）

### 1.2 任何 git 操作之前，先跑这一条

```bash
git status --porcelain                     # 改动清单（含未跟踪）
git stash list                             # 有没有别人存的半成品
git ls-files -u                            # 有没有冲突残留（非空 = 正在冲突中）
git log --oneline -3                       # HEAD 在哪
git branch --show-current                  # 当前分支
```

**只要前三条任一有输出，就进入「先保全」流程，不允许直接 pull / rebase / merge / 发布。**

### 1.3 什么算「要保全的东西」

| 类型 | 怎么认出来 | 保底线 |
|---|---|---|
| 已跟踪文件的改动 | `git status` 的 ` M` | 必须带着进提交或被 stash |
| **未跟踪的新文件** | `git status` 的 `??` | `git stash -u` 或 `git add` 进提交（**不带 `-u` 的 stash 会漏掉它们**） |
| 冲突残留 | `git ls-files -u` 非空 | 先解决或整体存档，**不要 `git add` 掉冲突标记** |
| stash 内容 | `git stash list` | 只增不减，绝不 `drop` / `clear` |
| 未推送的提交 | `git log @{u}..` | push 之前不删不改写 |

## 二、先保全：决策树

```
工作区有改动？
├── 能判断归属（就是本任务自己产生的）
│     └── ✅ 直接带着一起提交（首选）—— 见 3.1 的粒度
├── 判断不了归属 / 明显是别的会话在做的（比如全在 habits/ 而本任务是日历）
│     └── 存档二选一（都留可追溯记录）：
│           A. git stash push -u -m "<说明>"      ← 推荐，快，可 pop 回来
│           B. WIP 提交到临时分支                  ← 改动很大 / 要跨会话留着时用
│               git switch -c wip/<任务>-<时间>
│               git add -A && git commit -m "WIP: ..."
│               git switch -                      ← 回到原分支
└── 正在冲突中（git ls-files -u 非空）
      └── ❌ 停下，向用户报告两边分别改成什么样，由他选（绝不自动选边）
```

**存档之后必须记录**：把 stash 编号 / WIP 分支名写进当天的
`.workbuddy/memory/YYYY-MM-DD.md`，否则几天后没人知道 `stash@{2}` 是什么。

```bash
git stash push -u -m "2026-10-17 另一会话的打卡改动，本任务不动"
# 记下输出的 stash@{n}
```

## 三、提交与部署

### 3.1 提交粒度

| 原则 | 说明 |
|---|---|
| 一个逻辑改动一个提交 | 「修 bug」和「升版本号」分开；升版本号单独一个 `chore:` |
| 只提本任务的文件 | `git add <具体文件>`，不要 `git add -A`（会把别人的改动一起卷进来） |
| 提交信息带来源 | 见 3.2 |
| 本地验证过了才提交 | tsc + 单测 + 视觉守卫（网页端）；版本号自检（手机端） |

### 3.2 提交信息格式（**必带来源**）

```
<type>(<scope>): <一句话改了什么>

<为什么改 / 背景>

来源：<环境 · 会话> · 任务：<任务名>
```

例：

```
fix(calendar): 键盘弹起时点空白落到别的时间

坐标改在 pointerdown 那一刻算（tapSnap），避免按下时的坐标
配上抬起后的布局。

来源：Windows 本机 · 会话A · 任务：点空白落点修复
```

`来源` 这一行是**并行开发里唯一能事后追溯「谁改的、为什么」**的线索，不能省。

### 3.3 分支与标签策略

| 场景 | 做法 |
|---|---|
| 日常开发 | 只在 `dev` 上推；**不新建功能分支**（本项目是单人 + 多会话，分支只会增加合流成本） |
| 半成品要跨会话留着 | `wip/<任务>-<日期>` 临时分支（不推远端也行，本地留着就是备份点） |
| 要留可恢复快照 | `backup/<日期>-<简述>` 分支，或 stash 引用 |
| 发版 | 不切生产分支。**线上跑哪个版本记在 `~/.local/schedule/state/{web,app}.version`** |
| 打标签 | 只在用户要求时打，格式 `v2.0.8` |

### 3.4 冲突处理步骤（**绝不自动选边**）

```
1. git pull --rebase 失败 → 看 git status 里 "both modified" 的文件
2. 对每一个冲突文件：git diff 看两边分别改成什么
3. 能判断归属且明显是「我的改对了」→ 解决后 git add（不 commit，继续 rebase）
4. 判断不了 → git rebase --abort，回到干净状态，向用户报告：
      「文件 X：我这边的改动是 A，云端是 B，你要保留哪边？」
5. 用户拍板后再动手；整个过程工作区不得出现被丢弃的改动
```

### 3.5 部署（保全前提下的顺序）

```bash
# 0 体检：工作区必须干净（或已按第二节存档）、分支有上游、改动已推送
git status --porcelain && git log @{u}.. --oneline

# 1 网页端 / 服务端
./deploy/web-loop.sh            # 五段：可追溯 → tsc → 单测 → 深测 → 发布+实测

# 2 手机端（**必须在网页端之后**）
./deploy/mobile-loop.sh --device <IP:端口>

# 失败时
./deploy/publish-web.sh --rollback --approve # 网页端回上一份（**缺 --approve 只会 dry-run**）
./deploy/mobile-loop.sh --install-only      # 手机端重装机验证
git revert <坏的提交>                        # 代码层回退（**不用 reset**）
```

发布脚本自带体检（分支有上游 / 工作区干净 / 无未推送提交），
**不要用 `--allow-dirty` / `--allow-unpushed` 绕过它** —— 那等于让线上版本对不上任何提交。

## 四、安全网（三层）

| 层 | 检查 | 时机 |
|---|---|---|
| **提交前** | `git status --porcelain` 有内容才提交；`git ls-files -u` 必须为空；确认 `git add` 的文件清单里**没有别的任务的文件** | 每次 commit 前 |
| **推送前** | 先 `git pull --rebase`；失败按 3.4 处理；确认 `git log @{u}..` 就是要推的那些 | 每次 push 前 |
| **部署前** | ①工作区干净 ②HEAD 已推到 `dev` ③发布脚本体检通过 ④**备份点已留**（stash 引用或 `backup/` 分支） | 每次发布前 |

### 4.1 备份点怎么留

```bash
# 改动小、临时让路 → stash（记得带 -u）
git stash push -u -m "<说明>"

# 改动大、要留几天 → 备份分支（打引用即可，不用切过去）
git branch backup/2026-10-17-点空白修复

# 确认备份点存在
git stash list
git branch --list 'backup/*' 'wip/*'
```

备份点**只增不删**。要清理先问用户。

### 4.2 出了事故怎么救

| 情况 | 救法 |
|---|---|
| 误覆盖但未提交 | `git stash list` 找；没有就用编辑器撤销（IDE 本地历史） |
| 误提交了别人的改动 | `git revert <提交>`（保留历史），**不要 reset** |
| 误删了未跟踪文件 | 没有 git 记录 → 立刻停手，告诉用户，别再写盘 |
| 线上发坏了 | `publish-web.sh --rollback --approve`；APK 重装上一版（服务器留最近 3 份） |

## 五、给 AI 的速查卡

```
□ 动 git 之前：status / stash list / ls-files -u / log -3 / branch
□ 有别人的改动 → stash -u 或 wip 分支存档，并写进当天 memory
□ 只 add 本任务的文件，不 add -A
□ 提交信息带「来源：<环境 · 会话> · 任务：<名>」
□ 冲突 → 停下报告，不等用户选边就不动
□ 发布前：工作区干净 + 已推送 + 备份点已留
□ 绝不用 checkout -- / reset --hard / clean -fd / push -f / stash drop
```
