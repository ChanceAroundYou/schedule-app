## 三、数据模型演进（v3 → v4）

### 3.1 结构

```ts
// 同步元数据：每个实体都带
interface SyncMeta {
  id: string;          // 确定性 id，见 §3.2
  updatedAt: number;   // 实体级 LWW 时间戳（服务端权威）
  updatedBy: string;   // deviceId，时间戳相同时的平局破解
  deleted?: boolean;   // 墓碑，不物理删除
}

interface Task extends SyncMeta {
  title, note,
  date: string | null,      // null = 待办箱
  time: string | null,      // null = 未定时
  duration: number,
  done: boolean, doneAt: number | null,
  repeat: RepeatRule | null,
  seriesId: string | null,  // 重复系列根，见 §3.2
  repeatSeq: number,
  order: number,
  createdAt: number,
}

interface Habit extends SyncMeta { title, order, log: Record<string, true> }
```

**只有两处实质变化**：

1. 每个实体加 `updatedAt` / `updatedBy` / `deleted`（墓碑）
2. 重复实例加 `seriesId`，去掉随机 id

`ui.*`（主题、当前视图、侧栏顺序）**不进同步**，留本地 localStorage ——
它是设备偏好，不是数据。同步过去只会让手机改主题把桌面也改了。

### 3.2 确定性 id —— **本次重构最硬的骨头**

**问题**：现在 `DB.repeatAdvance()` 在勾选完成时**新建一个实例，id 随机**。
两台设备各自离线勾选同一条「每天」任务 → 各自新建一个实例 → 同步后**任务翻倍**。

RFC 5545 §3.8.4.4 明确：`RECURRENCE-ID` 对重复实例是**固定的**。CalDAV 作者在
RFC 4791 §3.2 也明确拒绝「物化重复实例」。原因是同一个：随机 id 的实例无法对账。

**方案**：实例 id **确定性派生**，不用随机数

```ts
// 独立任务：客户端生成 UUIDv4（离线可创建，天然唯一）
taskId = crypto.randomUUID()

// 重复实例：由「系列根 id + 发生日期」派生 —— 两台设备算出同一个
instanceId = `${seriesId}#${occurrenceDate}`   // 例：a3f…#2026-10-07
```

`seriesId` 本身是系列第一条任务的 UUIDv4，永不变。
`occurrenceDate` 是这次发生**原本应该在的日期**（不是实际完成日期）。

> 不用 `uuidv5`：可读形式 `${seriesId}#${date}` 已经确定性且能调试时肉眼对账，
> 哈希没有额外收益。

**同步路由**（曾经有人想改用 CRDT，但 Yjs 的 `uuidv4()`、Automerge 的
`ActorId::random()`、Loro 的「默认随机 u64」**全都要求随机 id**，与派生 id 直接冲突，
故排除）。

### 3.3 迁移

`normalize()` 已有的 v2→v3 迁移保留，新增 v3→v4：

- 给所有实体补 `updatedAt`（取 `createdAt` 或 `doneAt`）
- 给重复实例补 `seriesId`（从现有 `repeatSeq` 反推：找同标题 + 同 repeat 的任务组）
- `ui.*` 原地不动

**一次性归档**旧 key `schedule-app-v1` → `schedule-app-v1-archived-v3`，
不删除（用户可能在 legacy 版继续用）。

## 四、同步协议

### 4.1 设计取舍

调研结论：**没有任何现成方案自带离线同步**。

- Zero 官方文档：「Zero 不支持离线写入」
- Replicache 已归档（最后提交 2022-05-07）
- ElectricSQL 重写为只读
- PocketBase 作者：「有实时订阅，但没有离线/在线同步——这留给用户自行处理」

所以同步层**必须自写**，这反而使「不引入 PocketBase」成为更简单的选择
（省去 JSVM 里写并发逻辑）。

**采用**：服务端权威 + 客户端持久化发件箱 + **按字段 LWW** + 确定性 id。

> **为什么按字段而不是整实体**：op 里本来就只带改动的字段（客户端知道自己改了什么），
> 服务端逐字段比较和逐实体比较的代码量几乎一样。整实体 LWW 会让
> 「手机改标题 + 桌面改日期」变成一方被丢弃。

### 4.2 操作日志

```ts
interface Op {
  opId: string;        // 客户端 UUIDv4 —— 幂等键
  deviceId: string;
  ts: number;          // 客户端时钟（Date.now()）
  entity: 'task' | 'habit';
  entityId: string;
  fields: Record<string, unknown>;  // 只带改动字段
  deleted?: boolean;
}
```

### 4.3 端点

```http
POST /api/sync
  Authorization: Bearer <jwt>
  { "cursor": 12345, "ops": [ ...本地未发送... ] }
→ 200
  { "cursor": 12346,
    "applied": ["opId…"],          // 被接受的（含幂等跳过的）
    "rejected": [{"opId":"…","reason":"..."}],
    "ops": [ ...服务端自 cursor 以来的改动... ] }
```

单次往返，请求 + 响应同体。**没有 WebSocket / SSE**：

- SSE 没有游标、没有重放、没有顺序保证，PocketBase 的实测教训
- 家庭场景 2–3 台设备，进来就拉一次足够
- 前台每 60s 轮询一次「有没有新 cursor」，代价可忽略

### 4.4 服务端表

```sql
-- 用户（账本的 auth.json 单密码 → 多账户）
CREATE TABLE users (
  id TEXT PRIMARY KEY,          -- UUIDv4
  name TEXT NOT NULL,
  salt TEXT NOT NULL,
  hash TEXT NOT NULL,           -- sha256(salt + password)
  created_at INTEGER NOT NULL
);

-- 字段级 LWW 状态 —— 这是同步的核心，不是 实体表
CREATE TABLE field_state (
  user_id   TEXT NOT NULL,
  entity    TEXT NOT NULL,
  entity_id TEXT NOT NULL,
  field     TEXT NOT NULL,
  value     TEXT,                       -- JSON 编码
  ts        INTEGER NOT NULL,
  device_id TEXT NOT NULL,
  PRIMARY KEY (user_id, entity, entity_id, field)
);

-- 幂等：已处理过的 op，用于重放保护。定期按 ts 清理
CREATE TABLE applied_ops (
  user_id TEXT NOT NULL,
  op_id   TEXT NOT NULL,
  ts      INTEGER NOT NULL,
  PRIMARY KEY (user_id, op_id)
);

-- 游标：单调递增，客户端按它拉增量
CREATE SEQUENCE-like: cursor_meta(user_id TEXT PRIMARY KEY, seq INTEGER NOT NULL);

CREATE TABLE changes (          -- 自增游标驱动的变更流水
  user_id TEXT NOT NULL,
  seq     INTEGER NOT NULL,     -- 单调递增
  entity TEXT NOT NULL, entity_id TEXT NOT NULL, field TEXT NOT NULL,
  value TEXT, ts INTEGER NOT NULL, device_id TEXT NOT NULL,
  PRIMARY KEY (user_id, seq)
);
```

**写入是单事务**：`BEGIN IMMEDIATE` → 查 `applied_ops` → 逐字段比较 LWW → 写
`field_state` + `changes` → `COMMIT`。refer 账本 `putDoc()` 的写法。

**LWW 比较**：

```sql
-- 接受条件：更新的时间戳，或同时间戳下更大的 device_id（确定性平局破解）
INSERT INTO field_state … ON CONFLICT(…) DO UPDATE SET …
  WHERE excluded.ts > field_state.ts
     OR (excluded.ts = field_state.ts AND excluded.device_id > field_state.device_id)
```

> **不做 HLC（混合逻辑时钟）。** 家庭场景时钟偏移最多几秒，LWW 在秒级误差下
> 的实际影响是「偶尔某次编辑被覆盖」，可接受。代价是跨设备大批量离线编辑后
> 可能出现非线性顺序 —— 如果实测出问题，再升级到 HLC，届时只需要换
> `ts` 的生成与比较函数，表结构不变。

### 4.5 客户端发件箱

用 **Dexie 4**（IndexedDB 封装，Web + Capacitor 都可用）：

```ts
interface Outbox { opId, deviceId, ts, entity, entityId, fields, deleted }
```

每次编辑：**先写本地 IndexedDB（乐观更新 UI）→ 入队 outbox → 尝试 flush**。
断网时队列留存，下次进前台自动重试。

> **不用 OPFS**：Capacitor 里 OPFS 被拦（配置缺 `headers` 字段，issue #7813）。
> 也不用 `@capacitor-community/sqlite`：其 Web 端依赖 `jeep-sqlite`，
> 最后更新停在 2024-08-16。

**冲突 UI**：LWW 静默合并能覆盖 99% 的情况，不弹窗。仅当同一字段在
**双方离线期间**都被改过（`changes` 里有对方更新的 ts）时，在任务详情里
显示一条「此任务在另一台设备上被修改过」的提示 + 可查看旧值。

## 五、Android 小组件

### 5.1 数据通道

小组件是**独立进程**，不能启动 Activity，也不能读 IndexedDB。
唯一可行的通道是 **SharedPreferences**：

```text
App 每次数据变化
  → 序列化一份「小组件快照」JSON（今天未完成清单 / 下周概览 / 打卡状态）
  → @capacitor/preferences（MODE_PRIVATE，原生可读）
  → 发广播通知 widget 刷新
```

> `@capacitor/preferences` 8.0.1 底层就是 `MODE_PRIVATE` SharedPreferences，
> 原生 Kotlin 可以直接 `getSharedPreferences` 读到，这是选它的唯一原因。

**刷新时机**：

- `updatePeriodMillis` ≥ 30 分钟，且 Android 12+ 是不精确闹钟（±1 小时）
- 用户下拉 → `AlarmManager` 精确刷新
- App 内数据变化 → 显式广播（`AppWidgetManager.notifyAppWidgetViewDataChanged`）

### 5.2 多个小组件的分工

| 小组件 | 尺寸 | 内容 |
|---|---|---|
| 今日清单 | 4×2 | 今天未完成任务 + 勾选圈 |
| 下一件事 | 2×2 | 最近一个定时任务 + 倒计时 |
| 本周概览 | 4×4 | 7 天柱状密度 |
| 打卡 | 2×2 | 今日打卡进度环 |

**全部纯 `RemoteViews`**（不能 Compose）。勾选用 API 31+ 的 `CheckBox` +
`setOnCheckedChangeResponse()`，回调带 `EXTRA_CHECKED`；
31 以下降级为「点击进 App」。

> 注意：小米会完全忽略 `updatePeriodMillis`；`setRemoteAdapter(int, Intent)`
> 自 API 35 起废弃。

## 六、迭代阶段

每阶段有**明确出口条件**，不达标不进入下一阶段。

### P0 · 地基

拆目录、建 `app/` 的 Vite + TS + Tailwind、`server/` 骨架、ESLint 规则（禁 confirm / 禁 emoji）、
`legacy/` 冻结、nginx 加 `/schedule2/`。

**出口**：`npm run build` 出空壳；`tsc --noEmit` 干净；lint 规则能拦下故意写的 `confirm()` 和 emoji。

### P1 · 领域层（先于 UI，纯逻辑）

把 `parse.js`、`DB.repeatNext`/`repeatAdvance`、`Views.layoutOverlap` 搬进
`app/src/domain/`，**改成纯函数并补单测**（现在这些代码零测试）。

新增：确定性 id 生成、LWW 合并函数、op 回放。

**出口**：覆盖率 ≥ 80%；「跨两台设备各自推进同一重复任务 → 结果收敛到同一 id」
有专门测试用例。

### P2 · 后端

`users` / `field_state` / `applied_ops` / `changes` 建表、注册登录、JWT + jti 吊销、
`/api/sync` 幂等 + LWW。照账本 `server.js` 的结构写。

**出口**：`tests/api.test.js` 全绿，含三个关键用例 —— 重复投递同一 `opId` 只生效一次、
乱序投递后收敛到正确终态、并发同一字段取 LWW 赢家。`docker compose up` 能跑。

### P3 · 壳 + 设计系统

路由、主题（light/dark 两档，对齐现有）、Toast、Sheet、Dialog、
设计 token（颜色 / 间距 / 圆角 / 阴影 / 字号）、Icon 封装（统一 lucide）。

**出口**：Storybook 或一个内部 `/kitchen-sink` 页能展示全部组件；
390px 与 1440px 下都正常。

### P4 · 核心视图

日 / 周 / 月 + 待办箱 / 今天 / 逾期 / 已完成 / 打卡 / 垃圾箱。
**迁移现有视觉与布局约定**（CLAUDE.md §五 全部适用）：

- 高度 JS 实算，不写 `calc(100vh - N)`
- 月视图只写下限不均分，保证能滚
- 断点 900px，`isNarrow()` 与 CSS 媒体查询一致
- 顶栏不加 `position` / `z-index` / `sticky`
- 重叠任务按重叠簇分列

**出口**：与 legacy 版逐屏截图对比，无回归。

### P5 · 交互

- **拖拽排序**：现在是「让位洞」模型，靠直接改 DOM 顺序 + CSS transition。
  React 下不能这么做 —— **建议用 `dnd-kit`**（headless，pointer events + transform）。
  它用 transform 而非改 DOM，性能上等价甚至更好；当初拒绝 FLIP 是因为
  HTML5 拖拽每帧改 DOM 代价高，这个前提在 dnd-kit 下不成立。
  **仍需保留 `.tl-guide` 时间轴画线**（时间轴是连续坐标，没有「让位」概念）。
- **时间轴拉伸**：上下沿语义不同（下沿只改 `duration`，上沿同时改 `time`），
  自己用 pointer events 写比引库简单。
- **长按操作层**：`LONG_PRESS_MS = 480`，`pointerType !== 'mouse'` 时启用。
- **快捷键**、**自然语言解析**（接 P1 的纯函数）。
- **触屏无 hover**：所有 hover 显形元素在 `@media (hover: none)` 下常显。

**出口**：`tests/list-assert.mjs` 的断言在 React 版下同样能跑通（改动仅限选择器）。

### P6 · 离线 + PWA

Dexie 发件箱、Service Worker（Workbox 或手写）、manifest、
离线态 UI（顶栏一个小标）、重连自动 flush。

**出口**：断网后新建/编辑/勾选全可用，恢复网络后自动同步且无重复。

> **打包后的 Capacitor 应用源是 `https://{uuid}.androidplatform.net/`**，
> 与网站不同源 —— localStorage 独立。这是把数据搬到服务端的又一个理由。

### P7 · Android 壳

Capacitor 初始化、`cap sync`、签名、首启动把 legacy localStorage 数据导入服务端。

**出口**：真机装上能用，数据与网页版一致。

### P8 · 原生小组件

SharedPreferences 快照、四个 widget、刷新链路。

**出口**：OPPO 真机上四个 widget 都能加到桌面、勾选能回写。

### P9 · 切换

legacy 数据一次性迁移工具、`/schedule/` 切到新版、legacy 转为归档、更新文档。

**出口**：用户日常使用一周无问题后，`legacy/` 标记为只读归档。

## 七、多账户

表结构在 P2 就按多账户设计（`user_id` 进主键），**UI 后置到 P7 之后**。

- **首个注册的用户即管理员**（bootstrap，仅当 `users` 表为空时可注册）
- 之后由管理员在设置里创建账号 / 发邀请码
- 家庭场景不需要开放注册 —— 开放注册等于把日程本挂在公网

现有账本是**单密码**（`auth.json` 只有 `{salt, hash}`），这里必须扩成用户表。

## 八、已知硬骨头（按风险排序）

| # | 问题 | 影响 | 对策 |
|---|---|---|---|
| 1 | **重复实例随机 id → 跨设备翻倍** | 数据损坏 | §3.2 确定性派生 id，P1 专项测试 |
| 2 | **drag 让位洞在 React 下无法直搬** | 手感回归 | 评估 dnd-kit（P5），保留时间轴画线 |
| 3 | **无 HLC，时钟偏移下 LWW 可能反序** | 偶发覆盖 | 先做，实测有问题再升级（表结构不变） |
| 4 | **Capacitor 打包后 localStorage 与网站不同源** | 数据分裂 | 全部搬服务端，P7 做导入 |
| 5 | **小组件最小刷新 30 分钟且不精确** | 显示延迟 | 数据变化时显式广播 + 下拉刷新 |
| 6 | **legacy 数据迁移一次性** | 迁移失败=丢数据 | 归档不删除，保留回滚路径 |

## 九、不做的事

- ❌ 负一屏（OPPO 需商务对接）
- ❌ CRDT（要求的随机 id 与本项目派生 id 冲突）
- ❌ WebSocket / SSE（无游标无重放，轮询足够）
