## 二、仓库结构

现在是「源码即产物」的平铺布局。新版必须拆分为三个可独立构建的单元：

```text
日程管理/
├── app/                    React + TS 前端（Vite，独立构建）
│   ├── src/
│   │   ├── domain/         纯逻辑：模型 · 重复推进 · LWW 合并 · 解析器
│   │   ├── sync/           发件箱 · 游标 · 冲突处理
│   │   ├── data/           本地持久化（Dexie/IndexedDB）+ API 客户端
│   │   ├── ui/             设计系统：Button Sheet Dialog Toast Icon …
│   │   ├── views/          日 / 周 / 月 / 六个列表页
│   │   └── app/            路由 · 壳层 · 快捷键 · 主题
│   └── tests/
├── server/                 Node + SQLite 后端（只引 AI 那一组依赖，见 §一）
│   ├── server.js           HTTP 路由 + 鉴权 + 同步端点
│   ├── lib/db.js           SQLite：建表 · 迁移 · 查询
│   ├── lib/sync.js         幂等 · LWW · 游标
│   └── tests/
├── android/                Capacitor 壳 + 原生 Kotlin 小组件
│   └── app/src/main/java/…/widget/
├── legacy/                 现有纯静态版（冻结，只读，可回滚）
├── docs/                   计划 · 同步协议 · 设计系统
└── deploy/                 nginx conf · docker-compose
```

> `legacy/` 是**冻结的退路**：新版已经在 `/schedule/` 上跑（没有 `/schedule2/`），
> 出问题时把 `legacy/dist/` 的内容倒回 `dist/` 就退回旧版，
> 见 [DEPLOY-运维.md](../DEPLOY-运维.md) 第七节。

**关键：`domain/` 不含任何 React / DOM / 网络依赖**，是纯函数。
现有 `parse.js`、`DB.repeatNext`、`Views.layoutOverlap` 全部搬进这里，先补测试再改。

## 三、数据模型演进（v3 → v4）

### 3.1 结构

```ts
// 同步元数据：每个实体都带
interface SyncMeta {
  id: string;          // 确定性 id，见 §3.2
  updatedAt: number;   // 实体级 LWW 时间戳（服务端权威）
  updatedBy: string;   // deviceId，时间戳相同时的平局破解
  deleted?: boolean;   // 墓碑，不物理删除
}

interface Task extends SyncMeta {
  title, note,
  date: string | null,      // null = 待办箱
  time: string | null,      // null = 未定时
  duration: number,
  done: boolean, doneAt: number | null,
  repeat: RepeatRule | null,
  seriesId: string | null,  // 重复系列根，见 §3.2
  repeatSeq: number,
  order: number,
  createdAt: number,
}

interface Habit extends SyncMeta { title, order, log: Record<string, true> }
```

**只有两处实质变化**：

1. 每个实体加 `updatedAt` / `updatedBy` / `deleted`（墓碑）
2. 重复实例加 `seriesId`，去掉随机 id

`ui.*`（主题、当前视图、侧栏顺序）**不进同步**，留本地 localStorage ——
它是设备偏好，不是数据。同步过去只会让手机改主题把桌面也改了。

### 3.2 确定性 id —— **本次重构最硬的骨头**

**问题**：现在 `DB.repeatAdvance()` 在勾选完成时**新建一个实例，id 随机**。
两台设备各自离线勾选同一条「每天」任务 → 各自新建一个实例 → 同步后**任务翻倍**。

RFC 5545 §3.8.4.4 明确：`RECURRENCE-ID` 对重复实例是**固定的**。CalDAV 作者在
RFC 4791 §3.2 也明确拒绝「物化重复实例」。原因是同一个：随机 id 的实例无法对账。

**方案**：实例 id **确定性派生**，不用随机数

```ts
// 独立任务：客户端生成 UUIDv4（离线可创建，天然唯一）
taskId = crypto.randomUUID()

// 重复实例：由「系列根 id + 发生日期」派生 —— 两台设备算出同一个
instanceId = `${seriesId}#${occurrenceDate}`   // 例：a3f…#2026-10-07
```

`seriesId` 本身是系列第一条任务的 UUIDv4，永不变。
`occurrenceDate` 是这次发生**原本应该在的日期**（不是实际完成日期）。

> 不用 `uuidv5`：可读形式 `${seriesId}#${date}` 已经确定性且能调试时肉眼对账，
> 哈希没有额外收益。

**同步路由**（曾经有人想改用 CRDT，但 Yjs 的 `uuidv4()`、Automerge 的
`ActorId::random()`、Loro 的「默认随机 u64」**全都要求随机 id**，与派生 id 直接冲突，
故排除）。

### 3.3 迁移

`normalize()` 已有的 v2→v3 迁移保留，新增 v3→v4：

- 给所有实体补 `updatedAt`（取 `createdAt` 或 `doneAt`）
- 给重复实例补 `seriesId`（从现有 `repeatSeq` 反推：找同标题 + 同 repeat 的任务组）
- `ui.*` 原地不动

**一次性归档**旧 key `schedule-app-v1` → `schedule-app-v1-archived-v3`，
不删除（用户可能在 legacy 版继续用）。
