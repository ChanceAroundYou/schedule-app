# 架构决策 —— 为什么是现在这样

只记**结论与理由**，不记时间线。现状（结构、不变量、硬规则）看
[AGENTS.md](../AGENTS.md)，接口细节看 [接口.md](接口.md)。

## 一、选型

| 项 | 决定 | 理由 |
|---|---|---|
| 目标端 | Web 桌面 · Web 移动 · Android App | 用户既定 |
| 前端 | React 18 + TypeScript + Vite 6 | 与「个人账本」同栈，已验证 |
| 样式 | Tailwind 4 + 自绘语义样式模块 | 语义样式模块不带 `@layer`，**无层的作者样式赢过任何层内样式**，它才是设计系统；Tailwind 只用于新表面 |
| 图标 | `lucide-react` | **零 emoji**，全部语义 icon |
| 弹层 | 自绘 | **禁止原生 `confirm` / `alert` / `prompt`** |
| 后端 | 自写 Node（`node:http` + `node:sqlite`） | 标准库够用就用；有成熟库能省事就直接用，加一个说清理由（见三、5） |
| 安卓 | Capacitor 8 + 原生 Kotlin 小组件 | 见「五、小组件」 |
| 负一屏 | **不做** | OPPO 需商务对接，非技术门槛 |

## 二、同步为什么自写

**没有任何现成方案自带离线写入** —— 调研结论：

- Zero 官方文档：「Zero 不支持离线写入」
- Replicache 已归档（最后提交 2022-05-07）
- ElectricSQL 重写为只读
- PocketBase 作者：「有实时订阅，但没有离线/在线同步——这留给用户自行处理」

所以同步层**必须自写**，这也反过来让「不引入 PocketBase」成为更简单的选择。

**采用**：服务端权威 + 客户端持久化发件箱 + **逐字段 LWW** + 确定性 id + 全局游标。

| 取舍 | 结论 |
|---|---|
| **逐字段 LWW**（不是整条） | 整条 LWW 会吃掉对方改的别的字段。字段级状态落在服务端 `field_state` 表，客户端每个字段带 `_ts` / `_dev` |
| **全局单调游标**（不是每集一个） | `changes.seq` 是全局自增主键，客户端只存一个 `cursor`，服务端按 `cal_id IN (我的集)` 过滤 |
| **新加入的集要再拉一次全量** | 它的历史变更全在游标后面，光靠增量永远拉不到 —— 客户端看到不认识的 `calId` 就再要一次快照 |
| **集 / 成员 / 邀请不走 LWW** | 它们是「关系」不是「字段」，走普通 REST |
| **幂等不靠 oplog** | 比较键 `(ts, deviceId)` 创建时固定，重放一行不改 |
| **时间戳只拒绝、不钳制** | 钳制值取决于「收到请求的那一刻」，重放会钳出两个值 |
| **不做 CRDT** | Yjs / Automerge / Loro 都要求随机 id，与下面的派生 id 直接冲突 |

### 确定性 id —— 整个同步模型里最硬的一条

重复实例的 id **必须派生，不能随机**：`` `${seriesId}#${发生日}` ``。
两台设备离线勾选同一条「每天」任务，会**派生出同一个 id**，同步时合并成一条。
随机 id 会让任务翻倍（RFC 5545 §3.8.4.4 的 `RECURRENCE-ID`、RFC 4791 §3.2
拒绝「物化重复实例」，理由同源）。

- 独立任务：`crypto.randomUUID()`
- 重复实例：`${seriesId}#${原本应该在的发生日}`（不是实际完成日）
- 不用 `uuidv5`：可读形式调试时能肉眼对账，哈希没有额外收益

## 三、数据模型

| 决定 | 说明 |
|---|---|
| 同步元数据 | 每个实体带 `updatedAt` / `updatedBy` / `deleted`（墓碑，不物理删除） |
| 重复实例带 `seriesId` | 系列根 id 永不变 |
| **`ui.*` 不同步** | 主题、当前视图、侧栏顺序是**设备偏好**，留在 localStorage。同步过去只会让手机改主题把桌面也改了 |
| 本地持久化用 localStorage（key `schedule-app-v4`） | 数据量是「一个人的待办」，同步 API 就够，省一个依赖和一套异步封装。代价是 5 MB 上限与同步阻塞，真撞到再换 IndexedDB |
| 旧 key `schedule-app-v1` 归档不删除 | 退回旧版时旧数据还在 |

**后端依赖**：不追求「零依赖」。标准库够用就用标准库；有成熟库能把一段自写代码省掉，就用库。
加依赖前说清「标准库做不到什么」，并锁精确版本。目前唯一的运行时依赖是 AI 那一组
（`@earendil-works/pi-agent-core` + `pi-ai`），装在服务器本机磁盘，import 收在
`server/lib/ai/` 一个目录里 —— 与其手搓 agent 的工具循环 / 流式 / 工具结果回喂，不如接现成的。

## 四、多账户与共享

**开放注册，没有管理员，所有人平等**（上限 `MAX_USERS`，默认 200）。
用户之间靠**日程集**共享内容 —— 类似相册：一人可以有多个集，每个集单独设权限。

- **共享的单位是集，不是单条任务** —— 没有「把这一条任务分享给某人」这回事
- 加人是**两段式邀请**（发出去，对方接受才生效：`pending → accepted | declined | revoked`）
- 陌生人注册进来只会拿到一个空空的「我的日程」，看不到任何人的东西；
  频率限制兜住注册与邀请接口的滥用
- 曾经的「首个注册者成为管理员」方案**没有采用**：「管理员建账号」在家庭场景里
  等于多了一道人工关卡，换成邀请制共享之后这个顾虑不成立

## 五、小组件

小组件是**独立进程**，不能启动 Activity，也不能读 IndexedDB。
唯一可行的数据通道是 **SharedPreferences**：

```text
App 每次数据变化
  → 序列化一份「小组件快照」JSON（今天未完成清单 / 下周概览 / 打卡状态）
  → @capacitor/preferences（底层就是 MODE_PRIVATE SharedPreferences，原生可读）
  → 发广播通知 widget 刷新
```

> 选 `@capacitor/preferences` 的唯一原因就是它底层是 `MODE_PRIVATE`，
> 原生 Kotlin 可以直接 `getSharedPreferences` 读到。

系统对刷新间隔的限制（最小 30 分钟且不精确）靠**数据变化时显式广播 + 下拉刷新**补足。

## 六、明确不做的事

- ❌ 负一屏
- ❌ CRDT（要求的随机 id 与派生 id 冲突）
- ❌ WebSocket / SSE 作为同步通道（无游标无重放，轮询足够；AI 对话那条走 SSE 是另一回事）
- ❌ 服务端加密（鉴权归鉴权，存储归存储）
- ❌ 备忘录 / 笔记本 / 清单模块（已删，且是「丢掉」不是「归档」）
- ❌ 金额字段
- ❌ `v1` / `v2` 目录并存（结构变了就归档旧 key + 写迁移）

## 七、几个反直觉的既定结论

改这些之前先想清楚，它们都是踩出来的：

| 结论 | 原因 |
|---|---|
| **没有 `/schedule2/`，原地切换** | 一个人用的应用，并行两套的维护成本大于带来的安全感。回滚是换掉线上目录的内容 |
| **旧版 Service Worker 必须主动拆** | 旧版缓存里有旧版 `index.html`，是「怎么刷新都是旧界面」的根因。拆的时候要用 localStorage 标记锁成一次性，否则会把新版刚注册的那个也注销掉 |
| **点击走事件委托**（`#content` 上一个 `onClick`） | 行会被 React 重绘 / 拖拽重排替换掉，挂在行上的 handler 会跟着丢。代价是 `views/` 全纯展示、零回调 |
| **拖动期间不拉同步** | 远端变更落地 → 重绘 → 让位用的 transform 与占位洞全部重建，用户看到「拖到一半整个列表弹回原位」 |
| **后端数据放本机磁盘，不放工程目录** | 工程目录在 SMB 上，SQLite 的文件锁在 CIFS 上不可靠。见 [DEPLOY.md](../DEPLOY.md) |
| **没上 ESLint** | 零配置优先，禁止项靠 code review + 语义样式模块保证 |
| **很少用 Radix** | 沿用现有视觉是硬要求，Radix 的默认结构反而要拆掉重画 |
