# 接口一览

后端在 `server/`，Node 22 + `node:sqlite`，**只引 AI 那一组依赖**
（见 `CLAUDE.md` 六、1）。
线上只通过 nginx 的 `/schedule/api/` 反代暴露（`127.0.0.1:25692` 不直接对外）。

```bash
# 本地直连（开发时）
curl -s http://127.0.0.1:25692/api/health

# 线上（走 nginx）
curl -s https://home.xiaokubao.space/schedule/api/health
```

**没有版本号**，只有一套接口。所有请求与响应的 body 都是 JSON 对象。

## 认证

除了下表标「公开」的三条，其余都要带令牌：

```http
Authorization: Bearer <token>
```

令牌是自签的 JWT（`HS256`，密钥在数据目录的 `secret.key`，0600）。
**退出登录会把 jti 记进吊销表**，所以令牌是真的作废，不只是前端忘掉它。

密码用 `scrypt` 存（每个账户独立 salt），**不存明文、不存可逆哈希**。
用户名不存在时后端也会跑一遍 scrypt —— 否则响应时间会泄露「这个用户名在不在」。

| 接口 | 公开? |
|---|---|
| `GET /api/health` | ✅ |
| `POST /api/auth/register` | ✅ |
| `POST /api/auth/login` | ✅ |
| 其余 | ❌ 需要 `Authorization` |

**没有管理员。** 所有账户权限相同，注册开放（上限 `MAX_USERS`，默认 200，
见 `server.js`）。用户之间靠**日程集**共享内容，见下面那一段。

没有令牌 / 令牌过期 / 令牌被吊销 → `401 { "error": "…" }`。

## `GET /api/health`

存活探针。

```json
{ "ok": true, "time": 1791106800000 }
```

## `POST /api/auth/register`

开放注册。注册成功时**自动给他建一个「我的日程」**（不变量 1），
所以新账户一进去就有落脚点，不会是一片空白。

```json
// 请求
{ "name": "xiaokubao", "password": "……" }

// 200
{ "token": "eyJ…", "user": { "id": "…", "name": "xiaokubao", "createdAt": 1791224937633 } }
```

| 状态码 | 什么时候 |
|---|---|
| 400 | 用户名或密码不合规（长度等，见 `server/lib/auth.js` 的 `nameProblem` / `passwordProblem`） |
| 403 | 账户数已达 `MAX_USERS` |
| 409 | 用户名已存在 |
| 429 | 同一 IP 一小时内注册超过 10 次 |

## `POST /api/auth/login`

```json
// 请求
{ "name": "xiaokubao", "password": "……" }

// 200
{ "token": "eyJ…", "user": { "id": "…", "name": "xiaokubao", "createdAt": 1791224937633 } }

// 401
{ "error": "用户名或密码不对" }
```

> 用户不存在和密码错**返回同一句话**，不区分。

> 登录时也会过一遍 `ensureHasCalendar` —— 上次退出 / 被踢 / 集被删之后
> 可能一个集都不剩了，这里补上。

## `POST /api/auth/logout`

把当前令牌的 jti 记进吊销表。

```json
{ "ok": true }
```

## `GET /api/me`

**客户端启动只发这一个请求**就能拿到全部所需：我是谁、我有哪些集、谁邀请了我。

```json
{
  "user": { "id": "…", "name": "xiaokubao", "createdAt": 1791224937633 },
  "cals": [
    { "id": "…", "name": "我的日程", "ownerId": "…", "createdAt": 1791224937633, "role": "owner" }
  ],
  "invites": [ { "id": "…", "calId": "…", "calName": "我们家的", "role": "editor",
                 "createdAt": 1791224937633, "fromName": "妈妈", "toName": null } ]
}
```

`cals[].role` 是**我**在这个集里的角色，前端据此禁不禁用按钮。

## 日程集、成员与邀请

### 角色

| role | 能改内容 | 能改集与成员 | 界面文案 |
|---|:--:|:--:|---|
| `owner` | ✅ | ✅ | 创建者 |
| `editor` | ✅ | ❌ | 可编辑 |
| `viewer` | ❌ | ❌ | 只读 |

两条判断**只在 `server/lib/calendars.js` 里实现**（`canWrite` / `canManage`），
别在别处再写一遍 `if`。

**三条不变量**（破坏了用户就会卡在没法自救的状态里）：

1. 每个用户**始终**至少属于一个集 —— 退出 / 被踢 / 集被删之后自动补一个「我的日程」。
2. 每个集**始终**至少有一个 owner —— 最后一个 owner 不能降级、不能退出。
3. 权限判断只走 `db.roleOf()` 一处。

### 路由表

| 路由 | 谁可以 | 说明 |
|---|---|---|
| `GET /api/cals` | 登录 | 我可见的集 |
| `POST /api/cals` | 登录 | 新建，创建者自动成为 owner |
| `PATCH /api/cals/:calId` | owner | 改名 |
| `DELETE /api/cals/:calId` | owner | 删除（软删） |
| `POST /api/cals/:calId/leave` | 成员 | 自己退出 |
| `GET /api/cals/:calId/members` | 成员 | 成员名单 + 我发出去还没被接受的邀请 |
| `PATCH /api/cals/:calId/members/:userId` | owner | 改角色 |
| `DELETE /api/cals/:calId/members/:userId` | owner | 移出 |
| `POST /api/cals/:calId/invites` | owner | 发邀请 |
| `GET /api/cals/:calId/invites` | 成员 | 我发给这个集的、待处理的 |
| `GET /api/invites` | 登录 | **发给我的**待处理邀请（收件箱） |
| `POST /api/invites/:inviteId/accept` | 被邀请人 | 接受，此时才写进成员表 |
| `POST /api/invites/:inviteId/decline` | 被邀请人 | 谢绝 |
| `DELETE /api/invites/:inviteId` | 发出的人 / 集的 owner | 撤回 |

不在集里 → `404 { "error": "没有这个日程集" }`（**不区分「不存在」和「不归你」** ——
否则等于泄露了别人有哪些集）。权限不够 → `403`。

### `POST /api/cals`

```json
// 请求（name 留空就用默认名「我的日程」）
{ "name": "我们家的" }

// 200
{ "cal": { "id": "…", "name": "我们家的", "ownerId": "…", "createdAt": 1791224937633, "role": "owner" } }
```

名字最长 40 字，不能为空（留空走默认名）、不能含控制字符 → `400`。

### `GET /api/cals/:calId/members`

```json
{
  "members": [ { "id": "…", "name": "妈妈", "role": "owner", "joinedAt": 1791224937633 } ],
  "invites": [ { "id": "…", "calId": "…", "calName": "我们家的", "role": "editor",
                 "createdAt": 1791224937633, "fromName": null, "toName": "爸爸" } ],
  "myRole": "owner"
}
```

放在同一个响应里，因为界面上「成员」和「等对方确认」显示在同一块。

### `PATCH /api/cals/:calId/members/:userId`

```json
{ "role": "viewer" }
```

`400` 角色不对；**把最后一个 owner 降级也是 `400`**
（`至少要留一个创建者，请先把别人设成创建者`）。把自己提成 owner 允许 —— 协作里需要转让。

### `DELETE /api/cals/:calId/members/:userId`

踢人。踢不掉自己（`400 退出请用「退出日程集」`）。被踢的人如果因此一个集都不剩，
后端会自动给他补一个。

### 邀请

流程是**两段式**：owner 发出 → 对方在自己界面里接受 → 这时才写进成员表。
按用户名直接加人的话，输错一个字符就是把家庭日程交给了陌生人，而发出去的一方
看不到任何异常。

```json
// POST /api/cals/:calId/invites 请求
{ "name": "爸爸", "role": "editor" }

// 200
{ "ok": true, "invite": { "id": "…", "toName": "爸爸", "role": "editor", "status": "pending" } }
```

| 状态码 | 什么时候 |
|---|---|
| 400 | 角色不对 / 没填用户名 / 邀请自己 |
| 403 | 不是 owner |
| 404 | 没有这个用户名 |
| 409 | 这个人已经在这个集里了 |
| 429 | 同一 IP 一小时超过 30 次（这个接口会回答「某用户名存不存在」，所以卡得更严） |

邀请**不设过期**：家庭场景里发出去半年后才被接受是正常的，过期只会让用户反复重发。
要收回就撤回。

同一个人已经有待处理邀请时，旧的那条自动作废（`revoked`）再建新的 ——
否则对方接受其中一条、其余几条还挂在那里。

```json
// POST /api/invites/:inviteId/accept
{ "ok": true, "calId": "…", "role": "editor" }
```

- `403` 这条邀请不是给你的
- `404` 没有这条邀请 / 集已经不在了
- `409` 已经处理过了

> 接受之后**客户端要重新拉一次 `/api/me` 再同步**。集列表多了一个 → 引擎发现
> 不认识的 `calId`，会自动要一次全量快照。顺序反了就拉不到内容，见
> `app/src/ui/Calendars.tsx` 的 `InviteSheet`。

## `POST /api/sync`

**推和拉是同一次往返。** 客户端永远调这一个接口，不分开。

```json
// 请求
{
  "ops": [ { …op… } ],
  "cursor": 0,
  "deviceId": "devA"
}
```

`cursor = 0` 表示「我不知道服务器到哪了」（首次登录 / 换设备）→ 回**全量快照**；
`cursor > 0` 表示增量 → 回**自该游标之后的变更**。

### op 的形状

```json
{
  "opId": "本设备内唯一，用它划掉发件箱里已处理的条目",
  "deviceId": "设备标识（存在 localStorage 的 schedule-app-device）",
  "calId": "这条数据属于哪个日程集 —— 服务器靠它查权限",
  "entity": "task | habit",
  "entityId": "任务/打卡的 id",
  "ts": 1791106800000,
  "fields": { "title": "交周报", "time": "15:00" }
}
```

**一次 op 只带变了的字段**，不是整条任务 —— 这是「逐字段 LWW」的前提，
手机改标题、桌面改日期，两个改动都留得住。

`calId` 是**归属**，不是普通字段：把任务挪到另一个集 = 在目标集里建一个新实体 +
在源集里留一个墓碑（`app/src/data/store.ts` 的 `moveToCal()`）。

派生 id（重复任务的实例）形如 `a3f2…#2026-10-07`：`#` 前是系列 id，后是发生日。

### 响应

```json
{
  "applied":  ["opId1", "opId2"],
  "rejected": [ { "opId": "…", "code": "clock", "reason": "设备时间与服务器相差超过 24 小时，请校准后再同步" } ],

  // cursor = 0 时
  "cursor": 128,
  "snapshot": {
    "tasks":  { "id": { "id": "id", "calId": "…", "title": "…", "_ts": {}, "_dev": {} } },
    "habits": {}
  },

  // cursor > 0 时
  "cursor": 131,
  "changes": [ { "calId": "…", "entity": "task", "entityId": "…", "field": "title",
                 "value": "交周报", "ts": 0, "deviceId": "…" } ],
  "truncated": false
}
```

**先落盘再取数** —— 快照必须反映「本批 op 合并之后」的真值，
否则客户端会拿一个慢半拍的快照把自己的写入盖回去。

`applied` 里的 op 表示**已被处理**（不保证胜出），客户端据此把它们从发件箱划掉。
落败的字段会以对方的版本出现在本次响应附带的 `changes` 里，应用后自然收敛。

快照里每个实体都带 `calId`，客户端据此归位；**墓碑不进快照**
（客户端要的是「现在还活着的东西」，不是删除史）。

`rejected[].code` 决定客户端怎么处理：

| code | 含义 | 客户端该做什么 |
|---|---|---|
| `bad_request` | 这条 op 本身有问题，重试多少次都一样 | 丢掉，报错 |
| `clock` | 设备时钟不对 | **留着**，校准后重推 |
| `forbidden` | 这个集没有写权限（只读 / 已被移出） | 丢掉。**是终态**，重试也不会成功 |

> 看不到的集与写不了的集返回**同一个 `forbidden`**，不区分「不存在」和「不是你的」。
>
> 客户端在 `engine.ts` 里把三类分开处理：`bad_request` / `forbidden` 从发件箱
> 移除，`clock` 保留重试；遇到 `forbidden` 另外弹一次提示，因为用户看到的现象是
> 「点了没反应」，不说明会以为程序卡了。

### 常量

| 名 | 值 | 在哪 |
|---|---|---|
| 单次最多 op | 2000 | `sync.js` `MAX_OPS` |
| 单次最多回吐变更 | 5000（超了 `truncated: true`，下轮接着拉） | `sync.js` `MAX_PULL` |
| 单字段上限 | 64 KB（超了**静默丢弃**，不拖垮整批） | `sync.js` `MAX_FIELD_BYTES` |
| 时钟允许偏差 | 24 小时 | `sync.js` `MAX_SKEW_MS` |
| 请求体上限 | 16 MB | `server.js` `MAX_BODY` |
| 账户数上限 | 200（`MAX_USERS` 环境变量可改） | `server.js` `MAX_USERS` |

## 为什么不需要 oplog 做幂等

LWW 的比较键是 `(ts, deviceId)`，**两样都由客户端在创建 op 时固定**并持久化在
发件箱里。同一条 op 重放时比较键完全相同 → 既不是 `>`、也不是同值下更大的
deviceId → `ON CONFLICT` 的 `WHERE` 不成立 → **一行都不改**。

所以没必要额外建一张「这批 op 处理过了」的表，也没必要给 op 发号。

> **时间戳只拒绝、不钳制。** 钳制过一版：钳制值取决于「收到请求的那一刻」，
> 同一条 op 重放两次会钳出两个不同的时间戳，幂等性当场破掉（重放被当成新改动）。
> 现在改成超过 24 小时就退回并标 `clock`，客户端留着重试。

## 同步的范围只有我能看到的集

`pull()` 只查 `db.calendarIdsFor(userId)`，`snapshot()` 同理。所以

- 被移出某个集之后，那个集的变更**再也拉不到**；
- 但**本地已经下载的内容不会自动消失** —— 那是客户端的责任：
  `store.setCals()` 发现某个集不见了，会连它的实体一起清掉
  （见 `app/src/data/store.ts`）。

游标是**全局** `seq`，不是「每个集一个」：客户端因此只需要存一个数字。
代价是别人在别的集里写东西会让这个游标往前走（下次拉到的就是空的），
这是对的 —— 游标表达的是「我已经看到全世界第几号了」。

> **新加入一个集有个坑**：它的历史变更的 seq 早就低于我的游标了，光靠增量
> 永远拉不到。所以客户端一旦在 `cals` 里发现不认识的 `calId`，就强制来一次
> `cursor: 0` 的快照。改这块之前先读 `app/src/sync/engine.ts` 的 `refreshMeta()`。

## AI

模型是**任意 OpenAI 兼容端点**（本机的、Ollama、vLLM、各种网关都行），
配置由用户在界面上填、存服务器。端点实现在 `server/lib/ai/`，
业务上的约定（AI 是「另一台设备」、提案闸门）见 `CLAUDE.md` 二、AI。

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/ai/settings` | 读配置。**只回 `hasKey: true/false`，绝不回显 key** |
| `PUT` | `/api/ai/settings` | 写配置 |
| `POST` | `/api/ai/chat` | 发一轮对话，**SSE 流式**返回 |
| `POST` | `/api/ai/confirm` | 确认若干条提案 → **真正落库** |
| `GET` | `/api/ai/sessions` | 会话列表（只有 id / 标题 / 时间，不含消息） |
| `GET` | `/api/ai/sessions/:sessionId` | 一个会话的全部消息 + 未决提案 |
| `DELETE` | `/api/ai/sessions/:sessionId` | 删会话 |

`/chat` 与 `/confirm` 走限速（`rl.hitBoth`，按用户记）。`/chat` 一定要限 ——
它烧的是用户自己的额度。

### `GET` / `PUT /api/ai/settings`

```jsonc
// GET 响应
{ "provider": "openai", "baseUrl": "http://127.0.0.1:25001/v1",
  "model": "claude-sonnet-5.5",
  "hasKey": true,      // 有没有配 key。没配不一定不能用（本机网关就不需要）
  "ready": true }      // Base URL 和模型名都填了
```

```jsonc
// PUT 请求体，三个字段都可选
{ "baseUrl": "…", "model": "…", "apiKey": "…" }
```

> **`apiKey` 是三态**：**不传 = 保留原值，传空串 = 清空，传值 = 覆盖**。
> 设置浮层每次打开都读不到原 key（服务器不回显），所以它提交时只能
> 「用户真的改了 key 才带上这个字段」—— 一打开就保存不会把 key 抹掉，
> 靠的就是这个三态。

> key 明文落在 `schedule.db` 的 `ai_settings` 里，与 `secret.key` 同一级信任
> （靠数据目录的 nginx 404 + 文件权限隔离）。

### `POST /api/ai/chat`

```jsonc
// 请求
{ "sessionId": "…",          // 省略则新建
  "text": "下周哪天适合出去玩",
  "context": {               // 客户端补的「当前在看什么」，服务器不知道这些
    "today": "2026-10-06", "calId": "…", "nav": "calendar",
    "view": "week", "cursor": "2026-10-08" } }
```

响应是 `text/event-stream`，一行一个事件：`data: {"type":"…", …}`：

| `type` | 载荷 | 前端拿它做什么 |
|---|---|---|
| `session` | `{ sessionId }` | 新会话时记下 id |
| `text` | `{ delta }` | 追加到气泡（逐字） |
| `tool` | `{ phase: 'start'\|'end', name, args, isError, summary }` | 画「正在查 10月7日 的安排」那条动作条 |
| `proposal` | `{ proposal }` | 画一张**待确认卡片** |
| `done` | `{ sessionId, usage }` | 收尾 |
| `error` | `{ message, code }` | 错误条 |

> 用 SSE 而不是 `EventSource`：要 `POST`、要带 `Authorization` 头，
> 而 `EventSource` 两样都做不到 —— 前端用手写 `fetch` + `ReadableStream` 读
> （`app/src/ui/aiClient.ts`），切行的纯逻辑在 `app/src/domain/ai.ts` 的 `sseFeed()`。

> **nginx 那条 `^~ /schedule/api/ai/chat` 是必须的**：父块的
> `proxy_read_timeout 30s` 会让上游静默超过 30 秒的那一轮直接 504
> （建块时实测：30.03s 就 504，改 300s 后 35s 正常）。默认开着的
> `proxy_buffering` 也一并关掉 —— 那条在本机量不出差别，是标准写法的预防。
> 见 `DEPLOY.md` 4.4，那里把「实测过的」和「照惯例写的」分开列了。

### `POST /api/ai/confirm`

```jsonc
// 请求 —— **只有 id，没有一个可写字段**
{ "ids": ["toolu_…", "toolu_…"] }
```

```jsonc
// 响应。逐条独立处理，一条失败不影响别的
{ "done":   [{ "id": "…", "kind": "create", "calId": "…", "entityId": "…", "title": "买菜" }],
  "failed": [{ "id": "…", "reason": "「全家」你现在没有修改权限" }] }
```

**这是 AI 唯一真正写数据的地方。** 三条规矩（理由写在 `server/lib/ai/confirm.js`
的文件头）：

1. **只信 id 不信参数** —— 要写什么一律按 id 从库里把当时存的提案读回来。
   信客户端回传的 args 等于把权限判断交给浏览器。
2. **写之前重查一次权限** —— 提案生成到确认之间可能隔了几分钟，用户可能已经被
   降级成 viewer 或被移出那个集。
3. **写还是走 `sync.applyOps`** —— 那是全项目唯一的服务端写入闸门。
   AI 的 `deviceId` 固定 `'ai'`，所以它的改动会带 `_dev === 'ai'` 出现在客户端，
   也会正常参与逐字段 LWW 的冲突判定。

> 一次最多 50 条（`MAX_IDS`）。确认掉的提案会从消息里划掉，所以**重复确认同一条
> 会得到 `failed`「这条提案已经不在了」**——不是错误，是幂等。
>
> 提案的 id 就是模型那次工具调用的 `toolCallId`。

## 手工演练：两个人共用一个日程集

不需要界面就能走通全流程，方便排查。

```bash
B=https://home.xiaokubao.space/schedule

reg() { curl -s -X POST $B/api/auth/register -H 'Content-Type: application/json' \
  -d "{\"name\":\"$1\",\"password\":\"$2\"}" | grep -o '"token":"[^"]*"' | cut -d'"' -f4; }

TA=$(reg 妈妈 '……')
TB=$(reg 爸爸 '……')

# 妈妈拿到自己的集
CAL=$(curl -s $B/api/me -H "Authorization: Bearer $TA" | grep -o '"id":"[^"]*"' | head -1 | cut -d'"' -f4)

# 妈妈邀请爸爸（editor）；爸爸先去 /api/invites 拿 inviteId，再 accept
curl -s -X POST $B/api/cals/$CAL/invites -H "Authorization: Bearer $TA" \
  -H 'Content-Type: application/json' -d '{"name":"爸爸","role":"editor"}'
curl -s $B/api/invites -H "Authorization: Bearer $TB"
curl -s -X POST $B/api/invites/<inviteId>/accept -H "Authorization: Bearer $TB"
```

之后再 `GET /api/me`，两个人都应该看到这个集。

> **别把密码写进任何文件或脚本。** 上面这两行是从终端历史里粘的，
> 用完 `history -d` 清掉，或者干脆从标准输入喂。
